Een chatbot die alleen antwoordt vanuit mijn eigen projectteksten, met bronvermelding

Een Retrieval-Augmented Generation chatbot die bezoekers vragen laat stellen over mijn projecten, zoals “hoe loste Milan onderwerpherhaling op in de LinkedIn pipeline?”. Het antwoord komt uitsluitend uit mijn eigen case studies, met de bron erbij. Staat een antwoord niet in mijn teksten, dan zegt de bot dat, in plaats van iets te verzinnen. Live gehost op AWS en als widget ingebouwd in deze site.

Waarom dit project

RAG komt steeds terug in de vacatures waar ik naar kijk, en het was een vaardigheid die ik nog niet kon laten zien. Dit project dicht dat gat, en het is meteen een werkend onderdeel van mijn portfolio.

◆

Mijn rol

Ik bepaalde de architectuur en schreef de specificatie: wat de pipeline moet doen, welke onderdelen erin zitten, wat er niet in hoort (geen cloud-vectorstore, geen fine-tuning) en waar het mis kan gaan. Claude Code implementeerde dat. Ik testte elke stap zelf, stuurde bij op wat ik zag, en nam de uitrol op AWS persoonlijk door.

Problemen waar ik tegenaan liep
Bijna elk probleem stond letterlijk in de foutmelding
01

Mijn eigen bestanden werden niet gevonden

Ik had mijn teksten als .txt opgeslagen, maar de pipeline las alleen .md. Twee bestanden waren daarbij nog leeg. Ik paste de ingest aan en liet hem lege bestanden melden in plaats van ze stil over te slaan.

02

Gratis API-limiet

Voyage staat zonder betaalmethode maar 3 aanvragen per minuut toe. Tijdens het testen liep ik daar direct tegenaan. Zo leerde ik het verschil tussen een bug en een limiet herkennen.

03

Verminkte letters in de terminal

Op Windows werden ë en é verminkt. Het zat in de weergave, niet in de data. De fix was UTF-8 afdwingen bij het printen.

04

Docker startte niet

Docker Desktop miste een onderdeel van Windows (WSL). Na installeren en herstarten draaide alles.

05

Voorbeeldtekst als echte key

Op de server stond in mijn .env nog de placeholder-tekst in plaats van mijn echte keys. De fout “API key invalid” leek een Voyage-probleem. Een simpele controle van de lengte van de keys liet zien wat er mis was.

06

Server onbereikbaar ondanks certificaat

Mijn security group in AWS stond alleen poort 22 open, niet 80 en 443. In de logs van de proxy stond letterlijk: “likely firewall problem”. Na het openzetten van die poorten kwam het certificaat er meteen.

07

Een privésleutel in een projectmap

Mijn SSH-sleutel stond even in de projectmap, waar hij per ongeluk op GitHub of in een Docker-image had kunnen belanden. Ik zette hem veilig en liet git en Docker .pem-bestanden negeren.

Keuzes die ik bewust maakte
Klein houden, kosten vastleggen
01

Antwoord alleen uit mijn teksten

De grens “dit staat niet in mijn teksten” vind ik de kern van RAG. Een vraag over mijn opleiding, die niet in mijn content staat, beantwoordt de bot dan ook met precies dat, plus wat hij wel kan vertellen.

02

Embedding-cache

Embeddings kosten geld per aanroep. Door ze op te slaan per stukje tekst betaal ik bij een update alleen voor wat veranderd is.

03

Rate limit

Zodra het endpoint publiek werd, voegde ik een limiet toe per bezoeker en een dagelijks maximum voor iedereen samen. Zo ligt mijn maximale Claude-kosten vast, ook als iemand de bot probeert te spammen.

04

Eén kleine server

Docker met Caddy op één AWS t3.micro in Frankfurt, met een vast IP en HTTPS. Geen load balancer of autoscaling: dit is een portfolio-demo, geen productiesysteem. Lokaal gebruikte alles samen ongeveer 130 MB geheugen.

Wat ik geleerd heb
01

Hoe een RAG-pipeline in elkaar zit

Van chunking en embeddings tot retrieval en een system prompt die het model aan zijn bronnen bindt.

02

Content weegt zwaarder dan code

De kwaliteit van het antwoord hangt af van de kwaliteit en hoeveelheid van mijn eigen teksten, meer dan van de code. Bij te weinig content schiet de bot tekort, en dat is dan een contentprobleem.

03

Uitrollen op AWS

Een app verpakken met Docker en uitrollen: server, firewall, vast IP, domeinnaam en automatisch HTTPS.

04

Logs lezen in plaats van gokken

Bijna elk probleem stond letterlijk in de foutmelding.

05

Een API veilig publiek maken

Keys buiten git en Docker, een CORS-allowlist en een limiet op gebruik.
